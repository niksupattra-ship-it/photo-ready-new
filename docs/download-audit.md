# ประวัติสิทธิ์และการรับภาพสำหรับตรวจสอบปัญหา

ประวัตินี้ช่วยตรวจตามอีเมลว่า บัญชีมีหลักฐานรับสิทธิ์จากการชำระเงิน โค้ด หรือสิทธิ์ชดเชยหรือไม่ และหน้าเว็บรายงานว่าการส่งภาพไปถึงขั้นตอนไหน ใช้ตรวจปัญหาเป็นรายงาน ไม่ใช้ตัดสิทธิ์หรือปฏิเสธคืนเงินโดยอัตโนมัติ

การบันทึกทำงานเบื้องหลัง แยกจากการให้สิทธิ์ การหักเครดิต การชำระเงิน และการดาวน์โหลด เมื่อบันทึกประวัติไม่ได้ การรับภาพยังใช้เส้นทางเดิม ไม่มีป๊อปอัพเพิ่ม ไม่มีการให้สิทธิ์ซ้ำเพื่อสร้างประวัติ และไม่แก้เงื่อนไขโปร 89/159

## เปิดดูจากหน้า Railway

ผู้ดูแลดูข้อมูลได้จากหน้าฐานข้อมูลของ Railway ส่วนเว็บไซต์ `idpromth.com` ยังไม่มีเมนูผู้ดูแลสำหรับค้นประวัติ

1. เข้า Railway แล้วเปิดโปรเจ็กต์ของเว็บไซต์
2. คลิกบริการฐานข้อมูล **Postgres/PostgreSQL** แล้วเปิดแท็บ **Data**
3. คลิกตาราง **`download_attempts`** ดูคอลัมน์ `email_snapshot` เพื่อหาบัญชีลูกค้า จากนั้นดู `attempt_id` ของรายการที่ต้องการตรวจ และ `latest_rights` ซึ่งเป็นสิทธิ์ล่าสุดที่เซิร์ฟเวอร์อ่านได้เมื่อรับเหตุการณ์ของรายการนั้น
4. เปิดตาราง **`download_events`** แล้วเทียบ `attempt_id` เดียวกัน เพื่อดู `event_type` ว่าเกิดขั้นตอนไหน, `received_at` ว่าเซิร์ฟเวอร์รับข้อมูลเมื่อใด, `metadata` สำหรับขนาดไฟล์/วิธีบันทึก/รหัสข้อผิดพลาด และ `observer` สำหรับแหล่งที่มาของหลักฐาน

แถวที่มี `observer: server` เป็นผลตรวจสิทธิ์จากฐานข้อมูล ณ เวลารับเหตุการณ์ ส่วน `observer: client` เป็นเหตุการณ์ที่หน้าเว็บรายงาน เช่น กดดาวน์โหลดหรือกดบันทึก ยังไม่ยืนยันว่าไฟล์ถูกบันทึกลงอุปกรณ์สำเร็จ หากเวลาแสดงเป็น UTC หรือมี `+00`/`Z` ให้บวก 7 ชั่วโมงเพื่อเทียบเวลาไทย เวลาจากเครื่องลูกค้าใน `client_at` อาจคลาดเคลื่อนหรือส่งมาภายหลัง

Railway แสดงรายชื่อตาราง และคลิกตารางเพื่อเปิดรายการภายในได้ตาม [เอกสาร Database view ของ Railway](https://docs.railway.com/databases/database-view) ขั้นตอนนี้ใช้ดูข้อมูลในตารางโดยตรง หากต้องการรายงานรวมสิทธิ์ การชำระเงิน และเหตุการณ์ของอีเมลเดียวกัน ใช้คำสั่งในหัวข้อถัดไป

## รายงานรวมตามอีเมลด้วยคำสั่ง

ให้ผู้ดูแลรันจาก **runtime ของแอปใน Railway ที่มี `DATABASE_URL` อยู่แล้ว** ไม่ต้องเปิดฐานข้อมูลออกสู่สาธารณะ และไม่ต้องส่ง URL ฐานข้อมูล รหัสผ่าน หรือคีย์ลับในแชต

```sh
node scripts/check-download-history.mjs --email customer@example.com --days 30
```

หากต้องการผลลัพธ์แบบ JSON สำหรับตรวจละเอียด:

```sh
node scripts/check-download-history.mjs --email customer@example.com --days 30 --json
```

เปลี่ยน `customer@example.com` เป็นอีเมลที่ต้องการตรวจ `--days` รับ 1–365 วัน ค่าเริ่มต้น 30 วัน ช่วงเวลาคิดจากเวลาที่ฐานข้อมูลรับเหตุการณ์ ไม่ใช้เวลาจากอุปกรณ์ลูกค้าตัดช่วง รายการเหตุการณ์และหัวรายงานแบบอ่านข้อความแสดงเวลาไทย ส่วน timestamp ใน JSON และรายละเอียด ledger เป็น ISO ตาม UTC (บวก 7 ชั่วโมงเป็นเวลาไทย)

คำสั่งนี้ใช้ transaction แบบ **REPEATABLE READ READ ONLY** และจำกัดเวลาแต่ละคำสั่ง SQL ไม่มีการสร้างตาราง ให้สิทธิ์ หัก/เติมเครดิต เรียกเก็บเงิน คืนเงิน หรือติดต่อผู้ให้บริการชำระเงิน หากไม่มีตารางประวัติจะรายงาน `not_installed` และยังแสดงหลักฐานสิทธิ์จากตารางธุรกิจที่มีอยู่ หากบัญชีหาไม่พบหรือมีอีเมลตรงกันหลายบัญชีจะไม่รวมข้อมูลต่างบัญชีเข้าด้วยกัน

ผลลัพธ์แต่ละส่วนจำกัด 500 แถว และสิทธิ์ปัจจุบันตรวจจากงานตัวอย่างไม่เกิน 20 งาน ค่า `truncated: true` หมายถึงยังมีข้อมูลอื่นนอกผลลัพธ์ ให้ลด `--days` และตรวจวัน/งานที่เกี่ยวข้อง จำนวนใน `observations` นับเฉพาะแถวที่แสดงเท่านั้น สิทธิ์ชดเชยคงเหลือคำนวณจากยอดให้และยอดใช้ตลอดอายุบัญชี ไม่ใช่เฉพาะช่วงวันที่เลือก

ผลลัพธ์มีอีเมลและข้อมูลรายการของลูกค้า ให้เก็บและส่งต่อเฉพาะผู้ดูแลที่จำเป็นต่อการตรวจปัญหา ไม่มี session token รูปภาพ รหัสผ่าน ค่าโค้ดเต็ม หรือ hash ของโค้ดในรายงาน

## อ่านผลอย่างไร

| ส่วน/เหตุการณ์ | สิ่งที่ใช้ยืนยันได้ |
| --- | --- |
| `payments` | มีรายการในบัญชีรับชำระที่เซิร์ฟเวอร์บันทึกแล้ว แยก product ID และราคาอ้างอิงของโปรปัจจุบัน 89/159 กับโปรเดิม เช่น 119 |
| `receipts` | มีหลักฐานการปลดล็อกจากการชำระสำหรับ `workScope` นั้น พร้อมสถานะรายการซ้ำ/คืนเงินที่บันทึกไว้ |
| `codes` | ใช้โค้ดรับสิทธิ์กับงานแล้ว ไม่ใช่หลักฐานว่าชำระเงินจริง |
| `supportRedemptions` / `supportBalance` | ใช้สิทธิ์ชดเชยกับงานใดแล้ว และคงเหลือเท่าใด ไม่ใช่จำนวนครั้งที่ไฟล์บันทึกลงเครื่องสำเร็จ |
| `imageUnlocks` | ฐานข้อมูลให้สิทธิ์ภาพกับงานแล้ว ต้องดูงานกลุ่มเดียวกันและที่มาของสิทธิ์ร่วมกัน |
| `currentRights` | สิทธิ์ปัจจุบันของงานที่ยังมีอยู่ โดยอ่านฐานข้อมูลเท่านั้น ไม่ใช่สิทธิ์ย้อนหลัง และไม่ได้จำลองข้อยกเว้นเจ้าของระบบหรือบริบทเปิดงานเก่าที่บันทึกไว้ |
| `rights_observed` — `observer: server` | เซิร์ฟเวอร์ตรวจงานของบัญชีและสิทธิ์จากฐานข้อมูล ณ `receivedAt` จริง แยกสิทธิ์ดาวน์โหลดและทรงผม ไม่รับค่าสิทธิ์จากลูกค้ามายืนยัน |
| `download_clicked` — `observer: client` | หน้าเว็บรายงานว่าผู้ใช้กดดาวน์โหลด |
| `file_prepared` | หน้าเว็บรายงานว่าสร้างไฟล์พร้อมส่งแล้ว พร้อมขนาดภาพ ชนิดไฟล์ และจำนวนไบต์ที่รายงาน |
| `save_panel_opened` | เปิดหน้าบันทึกภาพบนมือถือ/แท็บเล็ตแล้ว ยังไม่ใช่การกดบันทึก |
| `download_requested` / `save_clicked` | ส่งคำขอให้เบราว์เซอร์ หรือกดลิงก์บันทึกภาพแล้ว ยังไม่ยืนยันว่าอุปกรณ์บันทึกไฟล์สำเร็จ |
| `share_handoff` | ระบบแชร์รับภาพต่อแล้ว ไม่ยืนยันว่าผู้ใช้เลือกแอปหรือบันทึกภาพปลายทางสำเร็จ |
| `share_cancelled` / `crop_cancelled` / `panel_closed` | ยกเลิกหรือปิดขั้นตอนนั้น ไม่จัดเป็นระบบดาวน์โหลดเสียโดยตัวมันเอง |
| `download_failed` / `rights_blocked` | หน้าเว็บรายงานข้อผิดพลาดหรือยังไม่ผ่านขั้นตอนอนุญาตส่งภาพ อาจเกี่ยวกับสิทธิ์ บัญชี ชุด หรือสถานะงาน ตรวจ `errorStage` / `errorCode` และเหตุการณ์ข้างเคียงประกอบ |

เหตุการณ์จากหน้าเว็บมี `observer: client` เสมอ และถือเป็นรายงานจากเบราว์เซอร์ เวลาจากเครื่องลูกค้า (`clientAt`) อาจคลาดเคลื่อน หรือส่งมาภายหลังเพราะออฟไลน์ ให้ใช้ `receivedAt` เป็นเวลาที่เซิร์ฟเวอร์รับข้อมูล สิทธิ์ที่แนบในเหตุการณ์เป็นการอ่านขณะรับข้อมูล ไม่ใช่การพิสูจน์สิทธิ์ ณ เวลาย้อนหลังที่อุปกรณ์ส่งมา

`mode` แยกโหมดง่าย/สตู/แบบเดิม `initiator` แยกผู้ใช้กดเองกับการส่งภาพอัตโนมัติหลังปลดล็อก `attemptId` รวมเหตุการณ์ของการรับภาพครั้งเดียว และ `workScopes` ผูกกับงานที่รับสิทธิ์ไว้ ไม่ให้นับการใช้สิทธิ์เป็นจำนวนดาวน์โหลดจริง การส่งซ้ำหลังเครือข่ายขัดข้องใช้ event ID เดิมเพื่อไม่เพิ่มแถวซ้ำ

## ขั้นตอนตรวจเคสลูกค้า

1. หาอีเมล วันเวลา และงานที่ลูกค้าแจ้ง ตรวจ `payments`/`receipts` หรือ `codes`/สิทธิ์ชดเชยก่อน โดยแยกที่มาของสิทธิ์ให้ถูกต้อง
2. เทียบ `workScope` และ `jobIds` กับภาพที่ลูกค้ากำลังรับ สิทธิ์ของภาพหนึ่งไม่ใช่หลักฐานว่าอีกภาพได้รับสิทธิ์ด้วย
3. ดู `rights_observed` ว่าปลดล็อกแล้วหรือไม่ และมี `premiumHair` ตามโปรหรือไม่ งานที่ลบตามอายุแล้วอาจตรวจสิทธิ์ปัจจุบันไม่ได้ ให้ใช้ snapshot เก่าที่มีเวลาเซิร์ฟเวอร์ประกอบ
4. ดูว่าถึง `file_prepared` แล้วหรือไม่ จากนั้นเป็นคำขอดาวน์โหลด บันทึก หรือแชร์ และมีข้อผิดพลาด/การยกเลิกตามมาหรือไม่
5. ถ้ามีเหตุขัดข้องให้ตรวจระบบและช่วยลูกค้ารับภาพตามสิทธิ์เดิม ประวัติไม่ใช่เหตุให้หักสิทธิ์เพิ่มหรือบังคับซื้อใหม่ หากไม่พบเหตุการณ์ ให้ถือว่า **ยังไม่มีหลักฐานรับเข้าระบบ** แล้วตรวจข้อมูลอื่นร่วมด้วย

อย่าสรุปว่า “ลูกค้าได้ภาพในเครื่องแน่นอน” จากการกดดาวน์โหลดหรือการส่งต่อแชร์ เบราว์เซอร์ไม่มีหลักฐานทั่วไปที่ยืนยันการเขียนไฟล์ลงเครื่องหรือ Photos สำเร็จทุกอุปกรณ์ การกดค้างที่รูปเพื่อบันทึกอาจตรวจไม่ได้ และเมื่อปิดแท็บ/ออฟไลน์/ปิดการเก็บข้อมูล บางเหตุการณ์อาจส่งไม่ถึงได้ ประวัติจึงช่วยแยกขั้นตอนที่พบปัญหา แต่ไม่พิสูจน์ว่าลูกค้าแจ้งเท็จหรือว่าระบบไม่เคยผิดพลาด

รายการ `payments`/`receipts` เป็นหลักฐานจากบัญชีแอป ไม่ใช่การตรวจธนาคาร/ผู้ให้บริการแบบสด ราคาในรายงานเป็นราคาของ product ID ที่กำหนดไว้ ไม่ใช่ยอดสุทธิหักค่าธรรมเนียมหรือยอดที่ตรวจจากใบเสร็จภายนอก รายการชำระซ้ำที่คืนเงินไม่ได้แปลว่าสิทธิ์จากรายการเดิมถูกเพิกถอน ต้องดู `overlap` และ `workScope` ประกอบ

## SQL สำหรับ PostgreSQL console

หลังติดตั้งตารางแล้ว ใช้ตัวอย่างนี้ดูเหตุการณ์ล่าสุด 500 แถวใน 30 วัน เปลี่ยนอีเมลตัวอย่างเพียงจุดเดียว ข้อมูลเป็นการอ่านอย่างเดียว ไม่มีข้อมูลรูปหรือคีย์ลับ:

```sql
BEGIN READ ONLY;
WITH target AS (
  SELECT lower('customer@example.com') AS email
), audit_users AS (
  SELECT u.id AS user_id FROM users u, target t
  WHERE lower(btrim(u.email)) = t.email
  UNION
  SELECT a.user_id FROM download_attempts a, target t
  WHERE a.email_snapshot = t.email
)
SELECT a.email_snapshot, e.received_at, e.client_at,
       a.attempt_id, a.mode, a.initiator,
       a.browser_family, a.device_class, a.job_ids, a.work_scopes,
       e.observer, e.event_type, e.metadata, e.rights_snapshot
FROM download_events e
JOIN download_attempts a
  ON a.user_id = e.user_id AND a.attempt_id = e.attempt_id
WHERE e.user_id IN (SELECT user_id FROM audit_users)
  AND e.received_at >= now() - interval '30 days'
ORDER BY e.received_at DESC, e.id DESC
LIMIT 500;
COMMIT;
```

SQL ตัวอย่างนี้ดูเฉพาะเหตุการณ์ หากยังไม่มีเหตุการณ์ให้ใช้ CLI ด้านบนดูบัญชีรับชำระ/สิทธิ์ด้วย CLI ตรวจอีเมลซ้ำก่อนอ่าน ส่วน SQL ให้ผู้ดูแลตรวจว่าตรงกับบัญชีเดียวกัน ห้ามนำไปเปิดเป็น endpoint สาธารณะ

## การเปิด/ปิดและอายุข้อมูล

- ตั้ง `DOWNLOAD_AUDIT_ENABLED=0` ใน runtime แล้วเริ่มแอปใหม่ เพื่อปิดการรับเหตุการณ์ โดยไม่ปิดเส้นทางรับภาพหรือเปลี่ยนสิทธิ์เดิม ตารางประวัติเดิมไม่ถูกลบ
- ตาราง `download_attempts` และ `download_events` แยกจากตารางงานที่บันทึกและการลบงานหลัง 45 วัน การลบงานไม่ได้ cascade ลบประวัตินี้
- เริ่มมีเหตุการณ์ใหม่หลังติดตั้งและลูกค้าใช้หน้าเว็บรุ่นที่มีการบันทึก ไม่สร้างประวัติดาวน์โหลดย้อนหลังขึ้นมาเอง รายการรับชำระ/สิทธิ์เก่ายังตรวจจากตารางเดิมได้
- เบราว์เซอร์มีคิวชั่วคราวที่จำกัดจำนวนและอายุ แยกตามบัญชี ไม่มีการเก็บ token หรือรูปในคิว การส่งซ้ำยังต้องยืนยันบัญชีและความเป็นเจ้าของงาน
- ประวัตินี้ไม่มีการใช้เป็นเงื่อนไขให้สิทธิ์ คืนสิทธิ์ หักเครดิต หรืออนุมัติ/ปฏิเสธคืนเงิน การกำหนดอายุเก็บประวัติของผู้ดูแลในอนาคตแยกจากเงื่อนไขเก็บงาน 45 วัน
